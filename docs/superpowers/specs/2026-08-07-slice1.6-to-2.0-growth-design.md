## 1. 决策摘要

用户已批准采用以下顺序：

```text
Slice 1.6  文本主链收口与地基加固
-> Slice 1.7  修改肤质重新筛选
-> Slice 1.8  verified-absence 成分排除
-> Slice 1.9  单图安全输入与索引地基
-> Slice 2.0  真实单图识别与找相似闭环
```

不采用：

1. 先做改肤质、把正式入口和前端缺陷留到后面；
2. 跳过文本收口直接做图片；
3. 把旧 Agent、Presenter、TurnParser、图片链或索引实现迁入新主链。

原因是当前独立 runtime 已能演示 Slice 1.5，但正式聊天 API 仍只接通首轮，
前端存在伪精确分数、错误吞没和跨会话竞态。继续加能力会把新逻辑建在没有
收口的入口上。

## 2. 总目标

到 Slice 2.0 收口时，工程必须具备：

- 一个权威的干净聊天入口；
- 防晒和修护精华的可靠文本多轮；
- 预算和肤质两类明确条件修改；
- 至少一条有正式 absence 证据的成分排除纵切，或一份经确认的 NO-GO 事实报告；
- 安全、强类型、会话归属明确的 1..4 图输入地基；
- 覆盖 103/103 真实商品图的新本地向量索引；
- 单图识别和找相似的真实浏览器闭环；
- 缺数据、缺索引、模型失败、客户端断流时全部 fail-closed。

## 3. 全局不变量

### 3.1 干净边界

- 新运行时不得 import `app.services` 或旧 V1/V2 主链。
- 旧代码只作失败案例和业务不变量参考。
- `application` 只编排，不拥有词表、评分、商品事实或展示推理。
- 具体 adapter 由 `app/guide_runtime/composition.py` 组装。
- presentation 不选品、不改序、不重新打分。
- LLM 不生成商品事实、候选 ID、分数或 winner。

### 3.2 事实边界

- Canonical 决定商品事实。
- verified absence 必须有明确审核来源。
- “成分表没写”不等于“不含”。
- raw OCR 不覆盖 Canonical。
- unknown 不改写成 matched 或 mismatch。
- conflict 不静默降级成 unknown。

### 3.3 决策边界

- 价格 unknown/conflict 继续 fail-closed。
- 功效硬约束 unknown/conflict 继续 fail-closed。
- 肤质采用 target-aware 三态：
  - 明确覆盖：matched；
  - 明确排除：mismatch；
  - 泛化、缺失或未明确覆盖：unknown。
- soft unknown 保留、排后并标注。
- business tie 不使用 product ID 伪造 winner。
- `deterministic_ranking.py` SHA 必须保持：
  `4737c18964f2be3502f036a87dd50e06965a214a87aa967c586d08e7c741f59f`。

### 3.4 状态边界

- 服务端状态是 query context 和最近实际展示候选的权威源。
- 客户端只回传 session ID、conversation version 和用户输入。
- 正常状态更新使用 CAS。
- clarify、error、stale、零候选和客户端断流不覆盖最近有效快照。
- 请求响应必须绑定不可变 session ID 和 request ID。
- 切换或删除会话必须中止其在途请求。

### 3.5 展示边界

- 前端只展示后端真实提供的离散证据和事实。
- 没有正式评分合同就不显示百分比。
- stage 和 decision process 必须对应实际执行步骤。
- 未运行知识检索时不得显示“知识检索已完成”。
- 未进行综合评分时不得显示“综合打分排序”。
- error 必须显示服务端脱敏文案并终止本轮。

## 4. Slice 1.6：文本主链收口与地基加固

### 4.1 目标

清零全局审计确认的 P1，使独立 runtime 和正式页面通过同一请求、SSE、状态和
浏览器合同。

本阶段不增加新品类，不增加新的追问类型，不接数据库、Milvus 或 LLM。

### 4.2 权威入口

`app.guide_runtime` 是干净主链的权威 composition root。

正式页面不得继续依赖 `app/api/v1/chat.py` 中基于当前消息关键词的临时分流。
接线采取以下原则：

1. 干净路由拥有 `ChatStreamRequest`；
2. `conversation_version` 从 HTTP 合同原样进入 `UserTurn`；
3. 首轮和后续追问都由服务端 session 状态判断；
4. 旧 Agent 不能成为干净追问的 fallback；
5. 旧 `/api/v1/chat/stream` 若保留，只能薄转发到同一干净路由，不能复制逻辑。

生产环境实际切流属于部署操作，执行前单独确认；仓库内合同统一可自主完成。

### 4.3 必修缺陷

1. 修复正式 API 多轮断路和固定 version 0。
2. 修复 target-aware 肤质三态。
3. 删除 `match_score=0.9/0.62/0.72` 和前端默认 `78%`。
4. 修复 SSE error 吞没。
5. 增加前端 request ownership、AbortController 和重复发送锁。
6. 将快照 CAS 移到商品/消息交付后、end 前。
7. 边界检查器覆盖真实编排器和非字面量动态 import。
8. 图片 manifest 与实际文件在 runtime composition 时 fail-closed。
9. 决策 evidence refs 增加规范化 skin 约束。
10. 把具体 adapter 组装移出业务编排文件。

### 4.4 正常流

```text
HTTP request
-> validate ChatStreamRequest
-> bind session_id + request_id + conversation_version
-> load server snapshot
-> route full query / candidate follow-up / budget revision
-> understand
-> plan
-> retrieve when required
-> decide
-> build response
-> emit decision_process
-> emit answer_contract
-> emit products
-> emit message
-> CAS save visible snapshot
-> emit end(new version)
```

### 4.5 失败流

```text
validation failure -> HTTP 422, no state
stale version -> clarify + end(authoritative version), no state
domain clarification -> clarify + end(current version), no state
internal failure -> error, no end, no state
client disconnect before visible delivery -> no state
CAS conflict -> clarify + end(latest version), no stale overwrite
session switch -> abort old request, no DOM write to new session
```

### 4.6 真实验收

必须同时在干净入口和正式页面执行：

1. 防晒首轮显示前 3 张真实卡片。
2. 修护精华首轮 `[91, 38]`。
3. `第二款呢` 返回 `[38]`，版本 `1 -> 2`。
4. `哪个更便宜` 返回 `[91]`，不声明综合最佳。
5. `预算降到100元呢` 返回 `[91]`，版本 `1 -> 2`。
6. `500元内干性修护精华` 保留 `[91, 38]` 为 unknown，不返回零候选。
7. 浏览器收到 `GUIDE_INTERNAL_ERROR` 时显示脱敏错误。
8. 在途请求切换会话时不串消息、不串版本。
9. 页面不出现无来源的 `% 契合`。
10. manifest 或图片 SHA 漂移时应用启动失败或健康检查失败。

### 4.7 退出门槛

- 审计中的 P1 全部有 RED-first 回归测试；
- 正式入口与独立 runtime 的契约测试共用同一 case matrix；
- 全量、runtime、双 boundary、CSV gate、Playwright 全绿；
- 独立 code review 无 P0-P2；
- 工作区干净并完成本地小步提交。

## 5. Slice 1.7：修改肤质重新筛选

### 5.1 目标

在现有服务端 `RecommendationQueryContext` 上支持明确肤质修改，只替换 skin，
继承品类、预算、功效和排除项，并重新执行完整推荐链。

### 5.2 支持表达

第一版仅接受明确目标：

- `改成敏感肌呢`
- `换成油皮`
- `那干皮呢`
- `按混合肌重新看`
- `改为中性肌`
- `那油敏肌呢`

不支持：

- `换个肤质`
- `更适合一点`
- `我最近有点红`
- 同一句同时修改预算和肤质；
- 从临时症状推断专业肤质。

包含完整品类的新输入仍按完整查询处理。

### 5.3 合同

```text
SkinRevisionDraft
  target?
  issue?

SkinRevisionPlan
  mode: revise | clarify
  constraints[]
  clarification?
```

合并规则：

1. 从服务端 query context 重建约束；
2. 删除旧 `SkinConstraint`；
3. 插入一个新 `SkinConstraint`；
4. 保留 category、budget、efficacy、exclusions；
5. 重新执行 retrieval、decision、presentation；
6. 成功有候选后 CAS 保存完整 context 和可见 candidates。

### 5.4 真实验收

核心两轮：

```text
500 元内修护精华
-> [91, 38]
-> winner_status = SELECTED
-> version 1

改成敏感肌呢
-> [91, 38]
-> winner_status = INSUFFICIENT_FOR_WINNER
-> version 2
```

候选可不变化，但 winner 状态必须变化，证明新肤质进入决策，而不是只改展示文案。

还必须覆盖：

- 无 snapshot；
- stale version；
- 非法或模糊肤质；
- 新结果零候选；
- presentation error；
- CAS conflict；
- 客户端伪造 query context；
- 后续 `第二款呢` 使用新快照。

### 5.5 退出门槛

- 六种受支持肤质均有解析和规划合同测试；
- target-aware 三态矩阵完整；
- 至少一条真实两轮浏览器门禁；
- 不修改排序内核；
- 不引入 LLM、旧意图链或文本历史反推。

## 6. Slice 1.8：verified-absence 成分排除

### 6.1 事实前提

当前受支持防晒和精华中没有一条 `verified_absences=known`。

因此本阶段先做事实审计，后做行为；禁止为了通过用例手写“不含酒精/香精”。

### 6.2 数据准入

一条 absence 事实必须包含：

- `product_id`
- 规范化成分/物质名
- 明确的“不含/无添加/free from”原始表述
- 正式来源 URL 或正式资料标识
- 获取时间
- source class
- 审核决定
- 审核人或批准记录
- source content SHA

仅有完整成分表但未出现某项，不满足 absence 准入。

### 6.3 执行分支

#### GO

若至少取得一条可审核的正式 absence 事实：

1. 用户复核并批准事实；
2. 更新 Canonical 和 manifest/SHA；
3. 增加明确成分排除修改；
4. 有 verified absence 的商品可通过；
5. known present 排除；
6. unknown/conflict 继续 fail-closed。

#### NO-GO

若没有可用正式来源：

1. 生成来源审计报告；
2. 不修改 Canonical；
3. 不开放“排除成功”能力；
4. 当前用户输入继续得到证据不足或零候选；
5. Slice 1.8 标记为事实阻塞，不伪造完成。

从 1.8 进入 1.9 前，GO 或 NO-GO 结论都必须由用户确认。

### 6.4 用户输入

GO 后第一版支持：

- `再排除酒精`
- `不要含香精的`
- `改成不含<规范化物质名>`

只允许单个明确排除项。多项同时修改、删除旧排除项和同轮复合修改另开设计。

### 6.5 真实验收

必须使用批准后的真实 Canonical：

- known present -> 排除；
- verified absence known -> 保留；
- absence unknown -> fail-closed；
- conflict -> fail-closed 并显示冲突；
- 两轮 context 正确继承；
- 前端不写“绝对安全”“零刺激”等越权文案。

## 7. Slice 1.9：单图安全输入与索引地基

### 7.1 目标

建立图片进入新主链所需的安全边界、身份、状态和可复现索引构建合同，但不返回
假相似商品。

### 7.2 输入限制

- JPEG、PNG、WebP；
- 单图最大 8 MB；
- 单次总大小最大 20 MB；
- 单图最大 20 百万像素；
- 一次 1..4 张；
- MIME、magic bytes 和真实解码一致；
- 拒绝动画图片；
- 拒绝解压炸弹；
- 同时最多 2 个图片推理任务。

### 7.3 会话合同

```text
ImageBundle
  bundle_id
  session_id
  owner_token_hash
  version
  images[1..4]
  expires_at

ImageObservation
  image_id
  ordinal
  content_sha256
  media_type
  width
  height
  image_kind
  ocr_evidence
  visual_candidates
  identity_status
  confidence
  errors[]
```

聊天请求只引用 `bundle_id`，不信任前端提交的候选事实。

### 7.4 所有权

- 匿名 session 同时持有不可猜测的 session token；
- bundle 必须同时匹配 session ID 和 token；
- 切换、删除、过期后旧 bundle 不可用；
- 只知道 bundle ID 不能读取或引用他人图片；
- 日志不记录原图、token 或完整 OCR 敏感文本。

### 7.5 索引合同

定义 `ImageRetrievalPort` 和本地构建器输入/输出，不下载模型、不生成零向量。

索引 manifest 必须包含：

```text
product_id
source_image_sha256
model_name
model_weights_sha256
preprocess_version
vector_dimension
vector_sha256
index_sha256
```

若未提供经批准的模型和权重，构建命令必须明确失败，不能写 placeholder index。

### 7.6 真实验收

- 用仓库真实 JPEG/PNG/WebP 样本验证解码；
- 用错误扩展名、错误 magic、超像素和动画样本验证拒绝；
- 1..4 图顺序和 image ID 稳定；
- bundle 归属、TTL、删除和并发限制通过；
- 103 张源图 manifest 全部可读且 SHA 一致；
- 未配置模型时明确 NO-GO，不产生索引文件；
- 浏览器支持多图预览，但不显示假识别结果。

## 8. Slice 2.0：真实单图识别与找相似闭环

### 8.1 前置拍板

开始真实向量构建前必须确认：

- 模型家族；
- 权重来源；
- 权重下载权限；
- 模型权重 SHA；
- 许可证；
- CPU 可接受延迟；
- 是否允许 GPU 作为可选加速。

默认架构仍是 `LocalNumpyImageIndex`。Milvus 不进入默认启动。

### 8.2 目标

跑通：

```text
真实上传
-> 安全解码
-> OCR/视觉观察
-> 视觉向量检索
-> Canonical 身份绑定
-> 硬条件决策
-> 商品卡
-> SSE
-> 浏览器
```

只有图片、没有文字时默认执行识别，不擅自推荐。

### 8.3 检索规则

- 索引覆盖 103/103；
- 查询和索引使用同一模型、权重和预处理版本；
- 相似度只负责召回；
- 预算、品类和否定词继续由文本精确约束处理；
- OCR 只用于身份过滤和证据提取；
- 相似度相同时 numeric product ID 升序；
- 未确认身份不能进入适配或比较 winner。

### 8.4 失败规则

- 解码失败：返回对应 image ID 的公开错误；
- 低置信或多个接近候选：请求用户确认；
- 索引 manifest/SHA 不一致：健康检查失败；
- 模型不可用：公开 error，不返回空成功；
- OCR 与 Canonical 冲突：Canonical 不被覆盖；
- 图片找不到候选：明确无结果，不回退颜色直方图；
- 不生成零向量或 placeholder vector。

### 8.5 真实验收

至少锁定：

1. 一张索引内真实商品图 top-1 命中自身 product ID。
2. 同图的缩放/重新编码版本 top-3 包含自身 product ID。
3. 两个不同商品查询顺序稳定。
4. 图像请求可叠加明确预算并执行硬过滤。
5. 缺索引和坏 SHA 时 `/health` 非 healthy。
6. 浏览器上传真实图片后显示候选、真实图片和详情链接。
7. 页面显示模型/索引版本，不显示无来源的“百分百识别”。
8. 全链不 import 旧图片服务、旧 Milvus 默认启动或旧 numpy 索引。

4. Slice 1.9 独立安全输入与索引地基计划；
5. Slice 2.0 在模型批准后写真实索引与单图闭环计划。

每个计划都必须产生可运行、可浏览器验收的软件或明确的 NO-GO 证据，不能把
未来阶段的未完成项包装成本阶段成功。

## 13. 总验收

到 2.0 收口时：

- 正式入口和独立 runtime 不再分叉；
- 文本首轮、候选追问、预算修改和肤质修改全部可多轮运行；
- 成分排除只基于批准事实；
- 前端不显示伪分数、假工具步骤或错误会话响应；
- 会话状态在断流、并发和切换时保持一致；
- 单图输入安全、身份稳定且归属明确；
- 新索引覆盖 103/103，manifest/SHA 可复现；
- 单图识别和找相似通过真实数据、HTTP 和 Playwright；
- 所有未知、冲突、缺索引和外部失败路径 fail-closed；
- 旧主链没有重新进入干净运行时。

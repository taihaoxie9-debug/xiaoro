# 商品知识覆盖收口设计

**日期：** 2026-08-31

**状态：** 已批准

## 1. 目标

把现有审核商品资料真正变成可稳定使用的最终 Demo 能力，而不是继续
新增一套知识系统。

完成后应满足：

1. 现有 1,079 条带 `answer` 权限的 ProductEvidence 都能在对应商品
   范围内被确定性检索；
2. FAQ、核心成分、用法、规格、肤质、质地、版本差异、包装异常、
   储存、批次和防伪等自然问法都能稳定回答；
3. 多方面问题可以使用多条互补证据，而不是检索出多条后只采用第一条；
4. 证据继续遵守 `answer`、`compare`、`hard_filter`、`soft_rank`、
   `weak_soft_rank` 和 `safety_gate` 权限；
5. 单品资料不得污染泛知识，不得把商家 FAQ 外推成普遍结论；
6. 缺少审核资料时明确回答缺口，不从原始商品描述、用户评论或模型常识
   补造事实。

本任务完成后，“泛知识 + 商品知识”达到最终 Demo 内容能力标准。
严格生产发布所需的线上监控、容量、供应商 SLA 和长期 Canary 不属于
本任务。

### 2.2 已有能力

当前商品知识链路已经具备：

```text
用户原话
  -> TurnMeaning 翻译问题含义
  -> Canonical 商品身份解析
  -> product_id 硬范围
  -> ProductEvidenceRetriever
  -> ProductEvidence + Category Facts 投影
  -> ProductKnowledgeAnswerPlan
  -> 商品卡、答案和证据事件
```

ProductEvidenceRetriever 已搜索：

- 用户原话；
- 模型翻译后的 `question_meaning`；
- `exact_text`；
- `plain_meaning`；
- `free_descriptors`；
- `relations`；
- `qualifiers`；
- FAQ 问答文本。

它使用中文二元/三元词面特征、英文词项和少量确定性桥接，不使用文本
向量。

### 2.3 实测结果

以下自然问法均把对应 FAQ 排在第一：

- “祖玛珑刚喷为什么一股酒精味？”
- “碧柔防晒打开会溢出来吗？”
- “碧柔防晒怎么涂才不搓泥？”
- “绿宝瓶第六代和旧版有什么区别？”
- “透明质酸钠修复贴低温出现白色结晶还能用吗？”

对全部 1,079 条 answerable ProductEvidence 使用其审核
`plain_meaning` 做机械可达性检查：

```text
Top1 = 1,079
Top5 = 1,079
Miss = 0
```

这证明基础检索器可达，不证明所有真实口语改写已经验收。

## 3. 关键问题

### 3.1 答案只充分使用第一条商品证据

检索器每个商品最多返回 5 条证据，总包最多 8 条，但
`_select_product_knowledge_facts()` 当前只优先采用第一条
`evidence:*` 事实，再补最多两条结构化事实。

因此用户同时询问：

```text
这款的核心成分、怎么用、低温结晶是不是正常？
```

即使三类证据都已召回，最终答案也可能只回答其中一个商品证据方面。

### 3.2 没有商品知识覆盖门禁

现有单测证明若干典型 FAQ 能命中，但没有一个发布门禁同时约束：

- 1,079 条 answerable 证据的机械可达性；
- 47 条 FAQ 的自然问题可达性；
- 常见字段问题的商品覆盖；
- 多方面问题的证据覆盖；
- 不相关证据、跨商品证据和错误变体不得进入答案；
- 重复运行结果必须一致。

### 3.3 商品资料仍有明确缺口

ProductEvidence 覆盖 86/103 个商品，Category Facts 覆盖 92/103 个。
二者覆盖并不等于每个商品都有核心成分、用法或 FAQ。

Canonical 中严格确认的 `ingredients_present` 目前只有 37/103 个商品。
商品证据可以补充一部分成分摘要，但仍有商品只能诚实回答“没有明确
标注”。

以下商品身份本身还需要治理，而不是补知识：

- PID 90：名称只有“理肤泉”；
- PID 100：名称为“000”；
- PID 26：产品身份字段为“无”。

这类记录不得通过猜测商品身份来补 FAQ。

### 3.4 原始 FAQ 不能直接发布

`seed_dump.sql` 和早期 `skincare_info.qa_facts` 中存在串商品、用户评论、
营销话术和不完整问答。

例如，科颜氏面霜记录中混入了白泥面膜去黑头问答。原始 FAQ 只能作为
候选发现来源，不能成为运行时证据。

运行时只能读取已经进入内容寻址 ProductEvidence，并满足：

```text
review_status = accepted
allowed_uses contains answer
subject_scope / variant_scope 可证明
```

## 4. 方案比较

### 4.1 方案 A：现有商品证据链覆盖收口（采用）

保留现有 ProductEvidenceRetriever，补：

- 覆盖感知的多证据答案组装；
- 全量确定性可达门禁；
- 自然改写矩阵；
- 商品与字段缺口报告；
- 真实后端、SSE 和浏览器验收。

优点：

- 不新增第二套系统；
- 复用已经审核的 1,079 条证据；
- 改动集中在答案组装和验证；
- 商品身份、权限和安全边界继续由代码控制。

### 4.2 方案 B：商品 FAQ 合并进泛知识库（拒绝）

问题：

- 单品营销容易被错误外推为普遍知识；
- 版本、规格和渠道差异会污染泛知识；
- 同一问法可能同时得到单品口径和通用口径；
- 破坏已经稳定的 22 主题 GeneralKnowledgeRetriever。

### 4.3 方案 C：增加商品文本向量召回（暂不采用）

商品已通过 `product_id` 将候选缩小到十几条，当前自然问法实测可以
Top1 命中。引入 embedding 会增加模型、索引、版本和漂移成本，但不能
解决答案只采用第一条证据的问题。

后续只有在自然改写门禁证明确定性召回存在系统性缺口时，才重新评估
受 product_id 和权限约束的向量候选信号。

## 5. 最终架构

泛知识和商品知识继续作为统一语义路径下的两个兄弟分支：

```text
TurnMeaning / StructuredUnderstanding / TaskPlan
                         |
                 Unified Router
                  /             \
      general_knowledge       product_knowledge
              |                     |
 GeneralKnowledgeRetriever  ProductEvidenceRetriever
              |                     |
 reviewed knowledge blocks  reviewed product evidence
              |                     |
 coverage + citations       coverage + product evidence
```

禁止：

- 合并两个 retriever；
- 新增第二个 dispatcher；
- 把商品 FAQ 发布到泛知识资产；
- 使用原始 `qa_facts` 直接回答；
- 让模型生成 product ID、evidence ID、事实或安全结论；
- 用问题原句、case ID、product ID 或 evidence ID 写生产特判；
- 引入文本向量。

## 6. “全部用上”的工程定义

“全部用上”不是每次回答展示全部资料，而是：

1. 每条带 `answer` 权限的证据都存在合法查询使其可被召回；
2. 每条证据只能进入其允许的消费场景；
3. 用户问一个方面时只给直接相关证据；
4. 用户问多个方面时，在公开答案预算内覆盖多个方面；
5. 超出一次回答预算的内容可通过后续追问继续获取；
6. 无直接证据时明确缺口；
7. `ambiguous`、`blocked`、`cross_product`、`duplicate`、
   `expired` 和 `irrelevant` 不进入普通答案。

## 7. 多证据答案组装

### 7.1 保留完整检索包

ProductEvidenceRetriever 继续返回当前最多 5 条/商品、8 条/包的排序
结果，不扩大模型上下文。

### 7.2 选择公开答案证据

ProductKnowledgeAnswerPlan 从投影中按以下顺序选择最多 3 个公开事实：

1. 直接命中用户当前问题的商品证据；
2. 覆盖尚未回答的 requested dimension；
3. 覆盖新的问题词面或关系；
4. 结构化 Category Fact 补充；
5. 相同字段、重复含义和同源重复不重复展示。

一个证据如果没有新增任何问题覆盖，不进入答案。

### 7.3 缺口输出

对明确请求但未覆盖的字段逐项说明：

```text
这款目前没有明确标注的核心成分信息。
```

对开放 FAQ 没有直接证据时：

```text
这款暂时没有与这个问题直接相关的明确信息。
```

安全问题没有安全证据时，继续输出现有安全缺口提示，不用普通商家宣传
填补。

## 8. 商品资料缺口治理

生成一份确定性覆盖清单，按商品记录：

- Canonical 身份是否有效；
- 是否存在 answerable ProductEvidence；
- 是否存在 Category Facts；
- 已覆盖字段；
- FAQ 数量；
- 缺失字段；
- 是否属于无效/占位商品身份。

处理规则：

1. 已有审核证据：接入答案，不重审原图；
2. 已有来源但未发布：必须回到原图和 scope 审核后再发布；
3. 只有原始 `qa_facts` 或用户评论：不发布；
4. 商品身份无效：进入 catalog cleanup，不猜测；
5. 没有资料：保留显式缺口。

本任务不承诺每个商品每个字段都有答案，只承诺不浪费已有可信资料，
且对未知保持诚实。

## 9. 验收

### 9.1 全量机械门禁

- answerable ProductEvidence：1,079/1,079 Top5 可达；
- 重复检索字节一致；
- 非 answer 证据普通问答命中数为 0；
- 跨商品和错误变体引用数为 0；
- 商品证据越权进入泛知识回答数为 0。

### 9.2 FAQ 与自然改写矩阵

覆盖全部 47 条 FAQ 的直接问题，并为以下类别建立审核过的自然改写：

- 核心成分；
- 使用方法；
- 规格与容量；
- 适合肤质；
- 质地与肤感；
- 新旧版差异；
- 包装异常；
- 储存和结晶；
- 批次和防伪；
- 商品特定安全边界。

常见改写、口语、省略商品名后的 current-item 追问均应命中同一审核
证据。

### 9.3 多方面回答

- 两到三个问题方面均有证据时，答案全部覆盖；
- 部分方面缺证据时，已覆盖内容正常回答，缺失项明确说明；
- 单方面问题不得塞入无关 FAQ；
- 最多三条公开事实，避免把商品资料整包倾倒给用户。

### 9.4 真实验收

使用真实模型、后端、SSE 和浏览器连续两轮验证至少：

1. 明确商品的核心成分；
2. FAQ 口语改写；
3. 版本区别；
4. 包装或储存异常；
5. current-item 追问；
6. 多方面问题；
7. 无证据商品；
8. 安全敏感问题。

每轮要求：

- 责任路由正确；
- 商品绑定正确；
- 预期证据命中；
- 无越权证据；
- 答案覆盖正确；
- 引用和商品卡可见；
- 无前端合同错误和控制台错误。

最后运行全量 pytest、架构门禁、反特判门禁、compileall 和 diff check。

## 10. 完成标准

本任务完成仅当：

- 泛知识现有 22 主题门禁继续全绿；
- 商品知识全量和自然改写门禁全绿；
- 多证据答案不再只采用第一条商品证据；
- 1,079 条 answerable 证据全部可达；
- 所有非 answer 证据保持不可回答；
- 原始脏 FAQ 没有进入运行时；
- 商品资料缺口清单完整；
- 两轮真实验收通过；
- 全量回归通过；
- 报告、提交、推送和远端 tree 校验完成。

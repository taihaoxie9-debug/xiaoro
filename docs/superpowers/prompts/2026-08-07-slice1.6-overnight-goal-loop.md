五、循环协议

Round 1：
- 完成启动审计。
- 读取全部事实源。
- 创建 docs/audits/slice1.6/loop_progress.md。
- 在 loop_progress.md 记录第一个未完成 Step 为 in progress，但不要提前勾选
  计划复选框。
- 记录起始 HEAD、旧仓库保护值和排序 SHA。

每个后续 Round：
1. 重新检查新仓库 git status。
2. 重新检查旧仓库 HEAD 和 status 指纹。
3. 读取计划中第一个未完成 Task。
4. 只处理该 Task 的范围，不顺手扩展功能。
5. 先写失败测试并实际运行，保存 RED 证据。
6. 写最小实现。
7. 运行 Task 指定的 focused tests。
8. 运行受影响的 broad tests 和 boundary。
9. 只有全部 GREEN 才勾选该 Task 已完成步骤。
10. 检查 git diff --check。
11. 在 loop_progress.md 追加 RED、GREEN、回归和保护值的真实摘要。
12. 只暂存该 Task 白名单文件及本轮计划/进度更新。
13. 创建计划指定的本地 Conventional Commit。
14. 继续下一 Task。

不要用“代码看起来对”代替命令证据。
不要在同一个提交混入不相关重构。
不要 amend 已有提交；修复失败创建新提交。

七、硬停止条件

出现任一条件立即停止施工，写入
docs/audits/slice1.6/morning_handoff.md：

- 旧仓库 HEAD、status 指纹或行数变化。
- 排序内核 SHA 变化。
- 需要修改 Canonical 商品事实。
- 需要选择业务语义、批准 verified absence 或放宽 fail-closed。
- 需要下载依赖、模型或访问网络。
- 需要修改禁止路径。
- 发现用户在新仓库中新增且无法安全合并的未提交修改。
- 需要执行 push、发布、部署或生产切流。
- 同一阻塞条件连续 3 个循环 Round 仍无法解除。

同一阻塞达到 3 轮时，不要继续重复报告；明确记录 blocked 原因、已尝试命令、
最小人工决策，并停止目标循环。

普通测试失败、实现困难、代码复杂不属于硬停止。先按 TDD 自行诊断和修复。

八、状态与前端不变量

- clarify、error、stale、零候选和客户端断流不改最近有效快照。
- products/message 交付前不能升 conversation version。
- 同一 session 的请求必须串行。
- 切换或删除 session 必须取消在途请求。
- 旧 session 响应不得写入新 session DOM 或 localStorage。
- 正式 API 必须透传 conversation_version。
- 第二款、最低价和预算修改不得掉回旧 Agent。
- “多种肤质适用”对未明确覆盖的目标是 unknown，不是 mismatch。
- 页面不得出现无来源的“% 契合”。
- Guide runtime 不得显示未执行的知识检索或综合评分步骤。
- SSE error 必须显示脱敏 message，且 error 后无 end。
